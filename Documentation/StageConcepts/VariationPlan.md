# 테마 바리에이션

`stage_capture` 브랜치의 숲·프로그램·폐허·동굴 네 테마를 **테마당 방 7종**으로 넓혔다. 방마다 동선, 바닥 형상, 랜드마크를 다르게 잡았다. 한 판은 지금처럼 방 5개다.

- 도착방 01
- 중간 전투방 3개: 02·03·04·06·07 중 시드로 고른다.
- 출구방 05

기존 리미널 스페이스 맵(`Assets/Liminal`의 방·스테이지·실행 씬)은 건드리지 않았다. 공유 갤러리 씬에서는 테마 구역만 갱신했다.

테마별 카탈로그: [판타지 숲](Previews/Variations/Forest_Catalog.jpg) · [프로그램 감옥](Previews/Variations/Digital_Catalog.jpg) · [멸망한 지구](Previews/Variations/Ruins_Catalog.jpg) · [동굴](Previews/Variations/Cave_Catalog.jpg). 방별 게임 카메라 화면은 `Previews/Variations/<방 ID>.jpg`에 있다.

## 1. 이전 테마 맵이 비슷하게 느껴진 이유

- **테마 안의 5개 방이 사실상 같은 방이었다.** 예전 `StageConceptScenery`는 방 번호에 따라 좌표를 0.5~1.5m 정도만 옮겼다. 같은 모델을 같은 쪽 벽에 같은 순서로 세우니 방이 바뀌어도 풍경이 그대로였다.
- **테마마다 Meshy 모델이 3종뿐이었다.** 방 하나에 10~15번씩 반복되어 실루엣이 금방 익숙해졌다.
- **네 테마의 구조가 같았다.**
  - 모두 중앙 5m 직선 통로였다.
  - 동쪽에는 큰 모델, 서쪽에는 작은 모델을 두었다.
  - 적 3마리도 모든 전투방에서 같은 좌표 `(-1.4,16) (1.4,23) (0,29)`에 나왔다.
- **화면의 70%를 차지하는 바닥이 단색 평면이었다.** 쿼터뷰 카메라는 55°로 내려다보므로 벽보다 바닥이 훨씬 많이 보인다.
- **화면 모서리에 빈 공간이 드러났다.** 동쪽 벽 너머가 비어 있어 게임 화면 오른쪽 위가 검게 보였다.

## 2. 게임 카메라 분석

값은 `IsometricFollowCamera` 기준이다.

- 테마 씬은 `pitch 55° · yaw 35° · distance 24`, 세로 FOV 36°를 쓴다.
- 휠로 4.5~24m를 조절하므로 24m가 가장 멀리 보는 상태다.
- 초점은 플레이어 발밑에서 0.55m 위다.

아래 표는 플레이어 발 위치를 원점으로 한 바닥 시야 범위다(x = 동쪽, z = 북쪽, 단위 m).

| 거리 · 화면비 | 카메라 위치 | 화면 네 모서리가 닿는 바닥 (좌상 · 우상 · 우하 · 좌하) |
| --- | --- | --- |
| 24m · 1.6 (캡처) | (-7.9, 20.2, -11.3) | (-6.1, 20.2) · (21.1, 1.2) · (4.2, -12.2) · (-12.9, -0.2) |
| 24m · 16:9 | (-7.9, 20.2, -11.3) | (-7.6, 21.3) · (22.6, 0.1) · (5.2, -12.9) · (-13.9, 0.4) |
| 16.5m · 16:9 (리미널 기본) | (-5.4, 14.1, -7.8) | (-5.2, 14.9) · (15.8, 0.2) · (3.7, -8.9) · (-9.6, 0.4) |

이 수치로 정한 배치 규칙이다. 28개 방 모두 이 규칙을 따른다.

1. **화면 방향.** 통로는 화면 오른쪽 아래에서 왼쪽 위로 비스듬히 지나간다.
   - 북쪽(+z, 출구 방향): 화면 왼쪽 위
   - 동쪽(+x): 화면 오른쪽 위
   - 서쪽: 화면 왼쪽 아래
   - 남쪽(입구): 화면 오른쪽 아래
2. **동쪽은 배경 구역이다.** 화면 오른쪽 위 모서리는 동쪽 벽(x=13) 밖으로 최대 8~9m 넘어간다.
   - 벽 안쪽 x=9~13과 바깥쪽 x=13~22에 높은 실루엣을 이어 세운다. 테마별로 나무 벽, 서버 탑, 건물, 동굴 벽이다.
   - 카메라 반대편이라 12m 넘게 높아도 플레이어를 가리지 않는다.
3. **서쪽은 낮은 전경이다.** 서쪽은 카메라와 플레이어 사이에 있다.
   - 통로에서 6m 안쪽 물체는 2.5m 이하로 둔다. 물체가 플레이어 쪽으로 1m 다가올 때마다 1.43m보다 높으면 발이 가려진다(tan 55°).
   - 서쪽 벽 바깥에는 1~3m 높이의 낮은 지형만 잇는다.
4. **한 화면은 약 21m 깊이다.** 한 번에 방 길이 36.4m의 절반쯤 보인다. 초점 요소를 z≈6 · 18 · 30 세 박자로 두어 어느 위치에서도 랜드마크가 하나 이상 화면에 들어오게 했다.
5. **바닥이 테마를 전달한다.** 연못, 개울, 도로, 회로, 수정 맥처럼 방마다 바닥 형상을 다르게 만들었다. 바닥은 다음 순서로 층을 쌓는다.
   1. 기본 재료
   2. 길
   3. 패치
   4. 가장자리
   5. 작은 흩뿌림
6. **크기 감각.** 24m 거리에서 1m는 화면 1000px 기준 약 52~64px이고, 플레이어는 약 60px이다. 0.5m보다 작은 소품은 잡음으로 읽히므로 1m 이상의 덩어리로 묶었다.
7. **전투 가독성.**
   - 적 스폰 주변 바닥은 중간 밝기의 잔잔한 무늬로 둔다.
   - 플레이어 부적은 시야선이 필요하고, 적은 장애물을 스피어캐스트로 피해 돈다. 그래서 엄폐물은 1~2개만 두고 틈은 1.2m 이상 비운다.
   - 물·구덩이 위 보이지 않는 충돌체는 0.7m 높이다. 적 회피(0.64~1.36m)에는 걸리지만 부적 시야선(1.0~1.2m)은 넘어가므로, 물 건너 적도 조준할 수 있다.
8. **시작방과 마지막 방.** 시작방은 입구 남쪽(z=-12~0), 마지막 방은 출구 북쪽(z=36.4~52)까지 화면에 들어온다. 두 곳 모두 방 밖 배경을 채웠다.
9. **방 이음매.** 방 순서는 셔플된다. 그래서 문(폭 6.8m) 양옆은 모든 방이 같은 높이 윤곽과 경계 장식으로 끝난다. 어떤 순서로 이어도 바닥과 배경이 끊기지 않는다.

## 4. Meshy 28종

생성 설정은 `meshy-7.1` text-to-3D, remesh 후 PBR 2K 텍스처다. 목표는 **모델당 15,000~30,000 삼각형**으로 합의했다(랜드마크 24k~30k, 소품 15k~22k).

| 테마 | 랜드마크 | 소품 |
| --- | --- | --- |
| 숲 | `fallen_giant_log` 쓰러진 거목 · `root_archway` 뿌리 아치 · `elven_shrine` 엘프 성소 · `guardian_statue` 수호자 석상 | `mossy_boulders` 이끼 바위 · `stone_lantern` 석등 · `wooden_footbridge` 나무 다리 |
| 프로그램 | `containment_pod` 수용 포드 · `sentinel_robot` 휴면 감시 로봇 | `security_turret` 감시 포탑 · `holo_terminal` 제어 단말 · `coolant_pipes` 냉각 배관 · `firewall_pylon` 방화벽 기둥 · `broken_server_rack` 쓰러진 서버 |
| 폐허 | `gas_station_ruin` 주유소 · `sandbag_bunker` 모래주머니 검문소 · `collapsed_billboard` 무너진 광고탑 | `concrete_barricade` 방호벽 · `burned_car` 불탄 차 · `bus_stop_ruin` 버스 정류장 · `rubble_pile` 잔해 더미 |
| 동굴 | `crystal_geode` 자수정 정동 · `cave_column` 석주 · `abyss_gate` 심연의 문 | `mine_cart` 광차 · `mine_support` 갱목 · `glow_fungus` 발광 버섯 · `mining_crates` 광부 물자 |

생성 결과:

- 28종 모두 사용 가능하다. 모델당 **13,386~30,912 삼각형**이고 합계는 595,398이다.
  - 목표 하한 15k보다 조금 적은 모델은 3종이다: 버스 정류장 13.4k, 방화벽 기둥 14.5k, 석등 14.9k.
- 사용량은 **900 Meshy API credits**로 상한 1,000 안이다. 재생성 3회를 포함한다.
  - 뿌리 아치는 첫 작업이 서버 오류로 실패해 다시 요청했다.
  - 방화벽 기둥과 광고탑은 형태가 틀린 첫 결과를 거부했다.
- 항목별 판정은 [meshy-variations-review.md](meshy-variations-review.md), 수치는 `meshy-variations.json`, 썸네일은 `Previews/Meshy/`에 있다.
- 방에는 새 28종과 기존 12종을 함께 배치했다. 고유 모델 40종, 배치 353곳이다. 기존 모델은 고목, 거대 버섯, 서버 모놀리스, 붕괴 건물, 수정 군집 등이다.

키는 **환경 변수 `MESHY_API_KEY`**로만 읽고 파일에 저장하지 않는다.

```text
python Tools/StageConcepts/meshy_variations.py plan            # 목록과 예상 크레딧
python Tools/StageConcepts/meshy_variations.py run --dry-run   # 요청 검사만, 전송 없음
python Tools/StageConcepts/meshy_variations.py run             # 생성 (중단 후 다시 실행하면 같은 작업을 이어받음)
python Tools/StageConcepts/meshy_variations.py reject --key crystal_geode --reason "정동이 닫혀 있음"
python Tools/StageConcepts/meshy_variations.py run --key crystal_geode   # 거부한 항목만 다시 생성
```

- 작업 ID와 원본은 git에서 제외된 `Tools/StageConcepts/Source/variations/`에 남는다. 다시 실행해도 유료 작업을 중복 제출하지 않는다.
- `--budget`(기본 1000)은 거부한 시도까지 합한 누적 사용량 상한이다.

## 5. 제작 파이프라인

방 레시피는 `Tools/StageConcepts/variations/`의 Python 코드다. 테마마다 파일이 하나씩 있다: `forest.py` · `digital.py` · `ruins.py` · `cave.py`. 여기서 Unity 자산을 직접 쓴다. 쓰는 방식은 Unity 6000.3 직렬화와 같다. 방 껍데기(바닥·벽·게이트·소켓·스폰)는 기존 프리팹에서 그대로 복사한다. 그래서 기존 스테이지, 씬, 갤러리의 참조는 모두 유지된다.

```text
python3 Tools/StageConcepts/variations/build.py --textures   # V2 표면 텍스처 (필요할 때만)
python3 Tools/StageConcepts/variations/build.py --unity      # 전체 빌드 (아래 목록 참고)
python3 Tools/StageConcepts/variations/build.py --preview OUT [--theme Forest --room 3]   # 게임 카메라 PNG
python3 Tools/StageConcepts/variations/validate.py [--room Forest_03]   # 이동 검사 단독 실행
python3 Tools/StageConcepts/variations/verify_unity.py                  # 참조·ID·스테이지 구조 검사
python3 Tools/StageConcepts/variations/gallery.py [--check]             # 공유 갤러리 동기화
```

`--unity`가 쓰는 것:

- 재질
- 방별 장식 메시(`Geometry/Variations`)
- 프리팹 28개
- 스테이지 4개
- 레이아웃 JSON(`Layouts`)
- 공유 갤러리 갱신
- 이동 검사

같은 입력이면 같은 파일이 나온다(여러 번 실행해도 해시가 같다).

미리보기는 게임 카메라와 같은 투영·조명으로 렌더한다. Unity 캡처와 평균 색 차이는 약 8% 이내다. 먼저 `preview_web`에서 `npm install`을 실행한다. Chromium 경로는 `CHROMIUM` 환경 변수로 바꿀 수 있다.

Unity 안에서는 **AC Roguelike → Stage Concepts → Rebuild Variation Rooms From Layout**을 쓴다. 같은 레이아웃 JSON으로 Unity 프리팹 API를 거쳐 방을 다시 만든다. **Build Four Theme Dungeons**는 이 경로로 방을 만든 뒤 스테이지, 씬, 갤러리까지 갱신한다.

## 7. 검증

Unity 에디터 없이 확인한 항목이다.

- **이동 경로 28/28.** `validate.py`는 `StageConceptValidation`의 이동 검사를 그대로 옮겼다. 저장된 프리팹의 실제 충돌체로 확인한다.
  - 격자와 캡슐: 0.5m 격자, Astraia 캡슐(반지름 0.24, 높이 1.65, 계단 0.24)
  - 목표 지점: 스폰에서 양쪽 문 접근점과 모든 적 스폰까지
  - 추가 검사 1: 바닥 높이인데 닿지 못하는 구역이 없다.
  - 추가 검사 2: 보이지 않는 차단벽 위에 올라설 수 없다.
  - 추가 검사 3: Forest_03 개울은 0.1m 격자로 확인해도 다리로만 건넌다. 이 검사로 다리 옆 틈을 찾아 막았다.
  - 추가 검사 4: 도착방마다 앞으로 2.2m 걷는 플레이 검사 경로가 비어 있다.
  - 결과: `variations-traversal.json`
- **Unity 자산 구조.** `verify_unity.py` 검사에서 문제 0건이다.
  - 방 28개의 fileID가 모두 고유하다.
  - 프리팹·메시·재질·GLB 참조가 모두 해결된다.
  - 스테이지 4개가 각각 방 8곳을 참조한다: 시작, 끝, 풀 5개.
  - Meshy 배치는 353곳이다.
- **공유 갤러리.** 원래 방 20개와 테마 방 28개, 모두 48개다. 참조, 부모·자식 목록, 방 간 겹침을 확인했다. `LiminalBackroomsValidation`의 갤러리 검사 조건(프리팹 수 = 갤러리 방 수)을 맞춘 것이다.
- **C# 컴파일.** Unity 6000.3.19f1 참조 어셈블리로 `Assembly-CSharp`와 `Assembly-CSharp-Editor`를 컴파일해 오류 없이 통과했다.

아직 Unity에서 직접 확인하지 않은 항목이다. 프로젝트를 열고 아래 메뉴를 한 번씩 실행하면 된다.

1. **Validate All Concepts**: 28방 기준으로 `validation.json`을 다시 만든다. 지금 저장소의 파일은 개편 전 20방 결과다.
2. **Validate Play Through All Themes**: 실제 CharacterController 이동, 전투, Victory를 확인하고 `play-validation.json`을 다시 만든다.
3. **Capture All Variation Rooms**: Unity 렌더로 방마다 전체 1장과 플레이 시점 3장을 `Previews/Variations/Unity/`에 저장한다.
4. **Capture Four Themes**: `Previews/*_Overview.png`, `*_Gameplay.png`를 새 01번 방으로 갱신한다.

성능 수치는 삼각형 수와 구성 기준이다. 특정 기기의 FPS를 측정한 것은 아니다.
