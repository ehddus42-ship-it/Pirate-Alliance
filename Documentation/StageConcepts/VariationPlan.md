# 테마 바리에이션 계획

`stage_capture` 브랜치의 숲·프로그램·폐허·동굴 네 테마를 **테마당 방 7종**으로 넓히고, 방마다 다른 동선과 랜드마크를 주는 개정 계획이다. 기존 리미널 스페이스 맵(`Assets/Liminal`)은 건드리지 않는다.

## 1. 지금 테마 맵이 비슷하게 느껴지는 이유

- **테마 안의 5개 방이 사실상 같은 방이다.** `StageConceptScenery`는 방 번호에 따라 좌표를 0.5~1.5m 정도만 옮긴다. 같은 모델을 같은 쪽 벽에 같은 순서로 세우므로 방이 바뀌어도 풍경이 그대로다.
- **테마마다 Meshy 모델이 3종뿐이다.** 방 하나에 10~15번 반복되니 실루엣이 금방 익숙해진다.
- **네 테마의 구조가 같다.** 모두 중앙 5m 직선 통로이고, 동쪽에 큰 모델, 서쪽에 작은 모델을 둔다. 적 3마리도 모든 전투방에서 같은 좌표 `(-1.4,16) (1.4,23) (0,29)`에 나온다.
- **화면의 70%를 차지하는 바닥이 단색 평면이다.** 쿼터뷰 카메라는 55°로 내려다보므로 벽보다 바닥이 훨씬 많이 보인다. 바닥의 모양과 재료가 단조로우면 방이 바뀌어도 화면이 거의 같아 보인다.
- **화면 모서리에 빈 공간이 드러난다.** 동쪽 벽 너머가 비어 있어 게임 화면 오른쪽 위에 검은 영역이 보인다.

## 2. 게임 카메라 분석

`IsometricFollowCamera` 기준 값이다. 테마 씬은 `pitch 55° · yaw 35° · distance 24`, 세로 FOV 36°를 쓴다. 휠로 4.5~24m를 조절하므로 24m가 가장 멀리 보는 상태다. 초점은 플레이어 발밑에서 0.55m 위다.

플레이어 발 위치를 원점으로 한 바닥 시야 범위다(x = 동쪽, z = 북쪽, 단위 m).

| 거리 · 화면비 | 카메라 위치 | 화면 네 모서리가 닿는 바닥 (좌상 · 우상 · 우하 · 좌하) |
| --- | --- | --- |
| 24m · 1.6 (캡처) | (-7.9, 20.2, -11.3) | (-6.1, 20.2) · (21.1, 1.2) · (4.2, -12.2) · (-12.9, -0.2) |
| 24m · 16:9 | (-7.9, 20.2, -11.3) | (-7.6, 21.3) · (22.6, 0.1) · (5.2, -12.9) · (-13.9, 0.4) |
| 16.5m · 16:9 (리미널 기본) | (-5.4, 14.1, -7.8) | (-5.2, 14.9) · (15.8, 0.2) · (3.7, -8.9) · (-9.6, 0.4) |

이 수치에서 나온 배치 규칙이다.

1. **화면 방향.** 북쪽(+z, 출구 방향)은 화면 **왼쪽 위**, 동쪽(+x)은 **오른쪽 위**, 서쪽은 **왼쪽 아래**, 남쪽(입구)은 **오른쪽 아래**다. 통로는 화면 오른쪽 아래에서 왼쪽 위로 비스듬히 지나간다.
2. **동쪽은 배경 구역이다.** 화면 오른쪽 위 모서리가 동쪽 벽(x=13) 밖으로 최대 8~9m 넘어간다. 벽 안쪽 x=9~13과 바깥쪽 x=13~22에 높은 실루엣(절벽, 나무 벽, 건물, 서버 탑, 동굴 벽)을 이어 세운다. 카메라 반대편이라 12m 넘게 높아도 플레이어를 가리지 않는다.
3. **서쪽은 낮은 전경이다.** 카메라와 플레이어 사이에 있으므로 통로에서 6m 안쪽 물체는 2.5m 이하로 둔다. 플레이어 쪽으로 1m 다가올 때마다 1.43m보다 높으면 발이 가려진다(tan 55°). 서쪽 벽 바깥은 1~3m 폭의 낮은 지형만 이어 붙인다.
4. **한 화면은 약 21m 깊이다.** 한 번에 방 길이 36.4m의 절반쯤 보인다. 초점 요소를 z≈6 · 18 · 30 세 박자로 두면 어느 위치에서도 화면 안에 랜드마크가 하나 이상 들어온다.
5. **바닥이 테마를 전달한다.** 연못, 개울, 도로, 회로, 수정 맥처럼 방마다 다른 바닥 형상을 만든다. 바닥은 기본 재료, 길, 패치, 가장자리, 작은 흩뿌림 순서로 층을 쌓는다.
6. **크기 감각.** 24m 거리에서 1m는 화면 1000px 기준 약 52~64px이고, 플레이어는 약 60px이다. 0.5m보다 작은 소품은 잡음으로 읽히니 1m 이상의 덩어리로 묶는다.
7. **전투 가독성.** 적 스폰 주변 바닥은 중간 밝기의 잔잔한 무늬로 둔다. 플레이어 부적은 시야선이 필요하고 적은 장애물을 스피어캐스트로 피해 돈다. 엄폐물은 1~2개만 두고, 틈은 1.2m 이상 비운다.
8. **시작방과 마지막 방.** 시작방은 입구 남쪽(z=-12~0), 마지막 방은 출구 북쪽(z=36.4~52)까지 화면에 들어온다. 두 곳 모두 방 밖 배경이 필요하다.

## 3. 새 Meshy 28종

생성 설정: `meshy-7.1` text-to-3D, remesh 후 PBR 2K 텍스처, **모델당 15,000~30,000 삼각형**(랜드마크 24k~30k, 소품 15k~22k). 기존 12종(3k~6k)보다 높은 기준으로 합의했다. 크레딧 예산은 **1,000**이다. 28종 × 약 30 크레딧 = 840이고, 나머지로 형태가 틀린 결과를 약 5회 다시 생성할 수 있다.

| 테마 | 랜드마크 | 소품 |
| --- | --- | --- |
| 숲 | `fallen_giant_log` 쓰러진 거목 · `root_archway` 뿌리 아치 · `elven_shrine` 엘프 성소 · `guardian_statue` 수호자 석상 | `mossy_boulders` 이끼 바위 · `stone_lantern` 석등 · `wooden_footbridge` 나무 다리 |
| 프로그램 | `containment_pod` 수용 포드 · `sentinel_robot` 휴면 감시 로봇 | `security_turret` 감시 포탑 · `holo_terminal` 제어 단말 · `coolant_pipes` 냉각 배관 · `firewall_pylon` 방화벽 기둥 · `broken_server_rack` 쓰러진 서버 |
| 폐허 | `gas_station_ruin` 주유소 · `sandbag_bunker` 모래주머니 검문소 · `collapsed_billboard` 무너진 광고탑 | `concrete_barricade` 방호벽 · `burned_car` 불탄 차 · `bus_stop_ruin` 버스 정류장 · `rubble_pile` 잔해 더미 |
| 동굴 | `crystal_geode` 자수정 정동 · `cave_column` 석주 · `abyss_gate` 심연의 문 | `mine_cart` 광차 · `mine_support` 갱목 · `glow_fungus` 발광 버섯 · `mining_crates` 광부 물자 |

프롬프트 원문과 목표 크기는 `Tools/StageConcepts/meshy_variations.py`의 `ASSETS` 표에 있다. 결과는 기존 규칙대로 `Assets/StageConcepts/Art/Meshy/<key>/<key>.glb`와 `provenance.json`에 저장한다.

### 생성 절차

키는 **환경 변수 `MESHY_API_KEY`**로만 읽고 파일에 저장하지 않는다.

```text
python Tools/StageConcepts/meshy_variations.py plan            # 목록과 예상 크레딧
python Tools/StageConcepts/meshy_variations.py run --dry-run   # 요청 검사만, 전송 없음
python Tools/StageConcepts/meshy_variations.py run             # 생성 (중단 후 다시 실행하면 같은 작업을 이어받음)
python Tools/StageConcepts/meshy_variations.py reject --key crystal_geode --reason "정동이 닫혀 있음"
python Tools/StageConcepts/meshy_variations.py run --key crystal_geode   # 거부한 항목만 다시 생성
```

- 작업 ID와 원본은 git에서 제외된 `Tools/StageConcepts/Source/variations/`에 남는다. 다시 실행해도 유료 작업을 중복 제출하지 않는다.
- `--budget`(기본 1000)은 거부한 시도까지 합한 누적 사용량 상한이다.
- 진행 요약은 `Documentation/StageConcepts/meshy-variations.json`에 기록된다.

방 구성, 빌드 절차와 검증 결과는 작업이 진행되면서 이 문서에 이어서 적는다.
